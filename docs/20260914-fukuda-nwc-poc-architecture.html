  • PC から EC2 へは SSM のポートフォワーディングで入り、EC2 から先は VPC エンドポイントだけで AWS のサービスに届く
  • エージェントは Knowledge Base をハイブリッド検索（ベクトル + キーワード）で候補 20 件を引き、リランクで 5 件に絞って Amazon Nova 2 Lite に渡す

  • 置いておくだけで 1 時間 ≈ $0.52（約 79 円）。OpenSearch Serverless だけで月 ≈ $240 かかるので、使わない期間は terraform/main を destroy する

構成図

左が VPC の中に置くもの、右が AWS のサービスです。VPC からサービスへの通信は、矢印に書いたエンドポイントを通ります。

会話 1 往復の流れ

  1. PC から EC2 の画面を開く。aws ssm start-session のポートフォワーディングで、PC の localhost:8080 を EC2 の 127.0.0.1:8080 へつなぎます。EC2 のセキュリティグループに受信ルールは要りません。
  2. EC2 がエージェントを呼ぶ。チャット Web が質問と会話 ID を InvokeAgentRuntime で送ります。署名は EC2 のインスタンスロールで行い、ブラウザには認証情報を置きません。
  3. エージェントが資料を検索する。質問文で Knowledge Base の Retrieve を呼びます。検索は HYBRID 指定で、OpenSearch Serverless がベクトル検索とキーワード検索を合わせた候補 20 件を出し、同じ呼び出しの中で Amazon Rerank 1.0 が質問との関係の深い順に並べ替えて、上位 5 件を返します。
  4. エージェントがモデルに尋ねる。資料と質問をまとめて Converse に渡します。ガードレールがまず質問を判定し、通れば Amazon Nova 2 Lite が資料をもとに答え、その回答もガードレールが判定します。
  5. 回答を返す。回答の末尾に参照した md のファイル名を付け、EC2 を経由してブラウザに表示します。ガードレールが止めたときは定型文を返し、その往復は会話の履歴に残しません。

手順書の md は、会話とは別に利用者が S3 に置き、取り込みジョブを流して OpenSearch Serverless に入れます。Knowledge Base は S3 を自動では見に行きません。

検索とガードレールの決めごと

決めたこと理由
検索はハイブリッド%BGP-5-ADJCHANGE のようなログの文字列やコマンド名は、意味の近さより文字の一致で当たるため
候補 20 件をリランクで 5 件に絞るハイブリッド検索の順位は点数の合算で、答えになっているかまでは見ないため。モデルに渡すのは 5 件のままなので、トークンは増えない
OpenSearch は Bedrock が呼ぶエージェントに要る権限が bedrock:Retrieve だけになり、VPC から出る先も bedrock-agent-runtime エンドポイントだけで済むため
判定するのは質問と回答だけ資料まで判定すると、手順書の「攻撃」「遮断」のような語で止まりやすく、判定の課金も増えるため
ガードレールは Standard 階層Classic 階層は日本語を判定できないため。判定は東京以外の APAC リージョンで行われることがある
個人情報フィルタは入れないIP アドレスやホスト名を伏せてしまい、運用の回答が壊れるため

デプロイから会話まで

  1. terraform/ecr を apply して ECR リポジトリを作る
  2. arm64 のエージェントイメージ（トポロジのツールと静的データ入り）をビルドして push する
  3. terraform/main を apply する。VPC / サブネット / ルートテーブルを作り、push したタグ agent_image_tag を渡す（OpenSearch の管理者は apply した人の認証情報から自動で取る）。VPC ID・サブネット・SG・バケット名は出力に出し、terraform/lab / terraform/stream / terraform/analytics / terraform/graph はローカルの state（terraform_remote_state）から読む
  4. Gradio の画面と wheel（arm64 / cp313）を S3 の web/ に置いて EC2 を再起動し、kb-docs/ の md を S3 に置いて取り込みジョブを流す
  5. Runtime のロググループに保持期間とタグを付け、利用者に ssm:StartSession の権限を渡す
  6. PC でポートフォワーディングを始め、ブラウザで http://localhost:8080/ を開く
  7. （任意）lab のイメージを ECR に、設定と containerlab の rpm を S3 に置き、terraform/lab を apply する。SSM セッションで入って sudo lab check
aws ssm start-session --region ap-northeast-1 \
  --target i-0123456789abcdef0 \
  --document-name AWS-StartPortForwardingSession \
  --parameters '{"portNumber":["8080"],"localPortNumber":["8080"]}'

各手順のコマンドは、リポジトリの README にあります。

フェーズ 2: containerlab → Telegraf → Kafka → Spark → S3 Tables と、トポロジの Neptune

フェーズ 1 では lab と Web はつながっておらず、トポロジもコンテナに焼いた静的データでした。 フェーズ 2 は 4 つのルート（terraform/lab → terraform/stream → terraform/analytics と terraform/graph）を足して、lab の SNMP を Kafka に流し、Spark で S3 Tables（Iceberg）に溜め、トポロジを Neptune に置きます（2026-09-17 のユーザー決定でフェーズ 2 の範囲をここまでにし、旧 2B を取り込みました。フェーズ 3 は terraform/workflow を足して、Temporal on ECS Fargate のワーカーがエージェントに原因を調査させ、人が Web の「承認」タブで承認すると lab で直します。エージェントのツールは AgentCore Gateway（MCP）経由。2026-09-17 着手。docs/phases.md）。 どれも時間課金なので、使う日に作って当日中に消す前提です。 

lab EC2 の Telegraf ── SNMP ポーリング（10 秒）+ SNMP trap（linkUp / linkDown）
      │ Kafka（IAM 認証）
      ▼
MSK（2 ブローカー）──┬─▶ detector Lambda ──▶ DynamoDB の異常テーブル ──▶ Web「異常一覧」/ エージェントの list_anomalies（「いま」）
                     ├─▶ MSK Connect（S3 sink）──▶ S3 の stream/（任意。CREATE_S3_SINK=0 で外す）
                     └─▶ Spark（EMR Serverless、60 秒トリガー）──▶ S3 Tables（Iceberg）の netops.snmp_metrics（履歴の正本）

Neptune ── Gremlin ──▶ エージェントのトポロジツール / Web「トポロジ」タブ（図・表・リンクの追加削除）
  • 異常の定義は「インタフェースが down」だけ。ポーリングで ifOperStatus が 2 になるか、snmpd が送る linkDown trap を受けたら open、up に戻れば resolved。BGP の隣接や経路の変化は見ません。
  • trap とポーリングの両方を持つのは、速さと確実さのため。trap は 5 秒以内に届きますが取りこぼすことがあり、ポーリングは 10 秒周期ですが必ず追いつきます。detector は同じ機器・同じインタフェースを 1 件にまとめます。
  • Web とエージェントは、同じ 3 つのモジュールでトポロジと異常を読みます。Neptune と DynamoDB の場所は SSM のパラメータから引き、無ければ静的データに戻る（60 秒キャッシュ）ので、フェーズ 2 を destroy してもフェーズ 1 のまま動きます。
  • Neptune の中身は Web から手で編集します。「静的データを投入」で 10 台と 10 本を入れ、以後リンクの追加・削除ができます。lab の実配線とは同期しません。
  • Spark は EMR Serverless（ARM64、emr-7.13.0 = Spark 3.5.6）で、ジョブが動いている間だけ課金。Telegraf の JSON をそのまま行（ts / topic / measurement / agent_host / host / tags_json / fields_json / ingested_at）にして追記します。閉域なので S3 Tables の API は s3tables の interface エンドポイント（2 AZ）経由。Kafka / MSK IAM / S3 Tables カタログの jar 6 本は ops/up.sh が Maven Central から取って S3 に置きます。
  • 費用はフェーズ 2 の 4 ルートで 1 時間 ≈ $0.69（約 104 円）。lab の t4g.large が $0.09、MSK kafka.t3.small × 2 が $0.12、MSK Connect 1 MCU が $0.14、lambda / sts のエンドポイントが $0.03、EMR Serverless の 2 vCPU が ≈ $0.15、s3tables のエンドポイント 2 AZ が $0.03、Neptune db.t4g.medium が $0.14。1 か月置くと ≈ $504（約 75,600 円）。東京の税抜単価で、2026-09-15（analytics は 2026-09-17）に AWS Price List API と料金ページで確認。

確認できていないこと

Terraform の 6 ルートは terraform validate と terraform fmt を通し、エージェントと detector と Neptune の読み書きは boto3 を差し替えた模擬テスト（41 / 23 / 18 項目）、analytics は Terraform と Spark スクリプトの整合の静的テスト（81 項目）を通しました。 Gradio の画面はフェーズ 1 の版は手元で起動し、フェーズ 2 の 3 タブ版は構文検査までです。AWS 上にはまだデプロイしていません。次の点は実環境で確かめる必要があります。

  • OpenSearch Serverless のアクセスポリシーの反映待ちで、インデックスの作成が 403 にならないか
  • 既定のアナライザで、日本語の質問にキーワード検索がどれだけ効くか
  • Amazon Rerank 1.0 が日本語の手順書で順位をどれだけ良くするか（日本語対応は AWS の文書で確認できていない）。候補 20 件 → 5 件が妥当か
  • 閉域の EC2 から、S3 ゲートウェイ経由で dnf install python3.13 / docker が通るか。t4g.small で Gradio が安定して動くか
  • containerlab の rpm が AL2023 で入り、lab の 14 コンテナが t4g.large で動くか。t4g.small $0.0216/h・t4g.large $0.0864/h は 2026-09-15 に Price List API で確認
  • VPC モードの Runtime が、イメージの取得に VPC 内の ECR / S3 エンドポイントを使うか
  • （フェーズ 2）Telegraf 1.40.0 の outputs.kafka が、インスタンスロールの資格情報で MSK の IAM 認証を通るか。MSK Connect の KafkaConnectVersion に 2.7.1 が入るか。Confluent の S3 sink 12.1.11 をプラグインとして登録できるか
  • （フェーズ 2）VPC モードの Runtime から Neptune のクラスター名が引けるか（プライベート DNS）
  • （フェーズ 2）EMR Serverless の emr-7.13.0 に S3 Tables カタログの jar が同梱されているか（同梱なら足した jar と衝突する可能性）。Kafka の jar 6 本の組み合わせで Structured Streaming の Kafka ソースが動くか。閉域から S3 Tables に届くか（interface エンドポイント + S3 ゲートウェイの *--table-s3）。Lake Formation の設定が要るか。組織の SCP / IAM が EMR Serverless / S3 Tables を止めていないか
