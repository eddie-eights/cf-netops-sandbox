  • 既存の閉域 VPC にチャット用の EC2 と AgentCore Runtime を置き、Bedrock の Claude Haiku 4.5 と会話する（NetOps フェーズ 1）

背景と前提

NetOps PoC のフェーズ 1 は「画面から AgentCore のエージェントと会話する」ところまでです。 社内の検証環境はインターネットへの出口を持たない閉域の VPC なので、同じことをその中で動かせるように CloudFormation で組みました。

  • VPC とサブネットは既存のものを使い、テンプレートでは作らない
  • インターネットゲートウェイ、NAT ゲートウェイ、EIP、パブリック IP を使わない
  • 利用者の PC は社内ネットワーク（Direct Connect か VPN）で VPC に届く

テンプレートは 2 つです。ecr.yaml がエージェントのイメージ置き場を作り、main.yaml がそれ以外の全部を作ります。 どちらも eddie-eights/cf-netops-sandbox にあります。

構成図

左の列が自分で置く計算資源、中央が VPC エンドポイント、右が AWS のサービスです。 計算資源からサービスへの通信は、必ず同じ高さのエンドポイントを通ります。

通信の順番

  1. PC がセッションを張る。aws ssm start-session（AWS-StartPortForwardingSession）が、社内ネットワーク経由で ssm / ssmmessages エンドポイントへつなぎます。入れるかどうかは IAM の ssm:StartSession で決まり、CloudTrail に残ります。
  2. EC2 は内側からつなぎに行く。SSM Agent が ssmmessages へ接続し、PC の localhost:8080 を EC2 の 127.0.0.1:8080 へ転送します。EC2 のセキュリティグループに受信ルールは要りません。
  3. チャット Web が Runtime を呼ぶ。AWS CLI の invoke-agent-runtime を bedrock-agentcore エンドポイントへ送ります。署名はインスタンスロールで行い、ブラウザには認証情報を置きません。AgentCore が VPC 内の Runtime にリクエストを渡します。
  4. Runtime が Bedrock を呼ぶ。bedrock-runtime エンドポイント経由で Converse を呼びます。モデルは jp.anthropic.claude-haiku-4-5-20251001-v1:0（パラメータ ModelId）です。ログは logs エンドポイントへ送ります。
  5. Runtime の起動時。ecr.api / ecr.dkr でイメージの情報を取り、レイヤーの実体は S3 ゲートウェイから取ります。
  6. EC2 の起動時。dnf が S3 ゲートウェイ経由で AL2023 のリポジトリから python3.13 を入れます（/usr/bin/python3 は 3.9 のため）。S3 ゲートウェイのポリシーは、ECR のレイヤーと AL2023 リポジトリの 2 つのバケットの読み取りだけを許します。

タグを付けられるリソースには、全部に次の 3 つを付けます。

Project=fukuda-nwc-poc owner=fukuda Name

IAM インスタンスプロファイル、EC2 の ENI、AgentCore が作るロググループと ENI にはタグが付きません。 ロググループだけは、デプロイ後に保持期間と一緒に手で付けます。

デプロイから会話まで

  1. ecr.yaml をデプロイして ECR リポジトリを作る
  2. arm64 のエージェントイメージをビルドして push する
  3. main.yaml をデプロイする（VPC、サブネット、ルートテーブル、イメージの URI を渡す）
  4. Runtime のロググループに保持期間とタグを付ける
  5. 利用者に ssm:StartSession の権限を渡す
  6. PC でポートフォワーディングを始め、ブラウザで http://localhost:8080/ を開く

6 の手順で PC から打つコマンドは次のとおりです。インスタンス ID はスタックの出力から取ります。 

aws ssm start-session --region ap-northeast-1 \
  --target i-0123456789abcdef0 \
  --document-name AWS-StartPortForwardingSession \
  --parameters '{"portNumber":["8080"],"localPortNumber":["8080"]}'

各手順のコマンドは、リポジトリの README にあります。

補足と確認できていないこと

テンプレートは cfn-lint を通し、EC2 のチャット Web は Python 3.13 で模擬テストしました。 ただし、AWS 上にはまだデプロイしていません。次の点は実環境で確かめる必要があります。

  • 閉域の EC2 から、S3 ゲートウェイ経由で AL2023 のリポジトリに届き、dnf install python3.13 が通るか
  • VPC モードの Runtime が、イメージの取得に VPC 内の ECR / S3 エンドポイントを使うのか、サービス側で取得するのか（安全側に倒してエンドポイントを作る設定を既定にした）
  • SSM Agent のポートフォワーディングが localhost を IPv6 で先に試すか（Web は 127.0.0.1 だけで待つ）
  • Session Manager plugin が社内プロキシの環境変数に従うか
  • Runtime のロググループが作られるタイミング

この構成に入っていないものもあります。

  • 会話の永続化。履歴は Runtime のセッションの中にだけあり、アイドル 5 分か画面の再読み込みで消える
  • チャット Web のログの CloudWatch Logs 転送
  • 多人数の同時利用。t4g.micro で数人程度まで
